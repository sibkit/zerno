# Как это устроено

Записка для того, кто вернётся к проекту без памяти о том, как он делался.
Здесь только неочевидное: решения и их причины, найденные ловушки, замеры.
Что умеет программа и как ей пользоваться — в `README.md`.

---

## 1. Карта кода

```
index.html          только разметка: каркас страницы и список подключений
static/css/         оформление: tokens → base → layout → components/*
static/js/          движок и интерфейс на JS (запасной путь), 14 модулей
src/main.zig        HTTP-сервер: маршруты, кэш полей, раздача статики, библиотека
src/engine.zig      шум, композит, дизеринг
src/color.zig       Oklab / OKHSL
src/doc.zig         модель документа и строгий разбор JSON
src/test.zig        тесты движка Zig      (zig build test)
src/bench.zig       замеры                (zig build bench)
tests/              проверки на Node: ядро JS, паритет движков, интерфейс в jsdom
noises/             библиотека пресетов
```

Порядок появления: сначала было только `index.html` (всё считалось в браузере),
потом добавился сервер на Zig. Браузерный движок **не выброшен намеренно** —
страница обязана работать при открытии файлом, без сервера.

### Почему `static/` разложен именно так

Раньше стили и весь скрипт жили внутри `index.html` — файл дорос до 2600 строк,
и найти в нём нужное правило или функцию стало заметно дольше, чем написать.
Разложено по слоям:

```
static/css/tokens.css        только переменные: палитра, радиусы, шрифты
static/css/base.css          сброс, типографика документа, полосы прокрутки
static/css/layout.css        каркас: сетка приложения, три колонки, брейкпоинт
static/css/components/*.css  оформление узлов: панель, кнопки, поля, сцена, …
static/js/color.js           Oklab / OKHSL
static/js/lattice.js         хэш и периодические решётки
static/js/field.js           октавы, искажение домена, кэш полей
static/js/shape.js           форма значения и цветовая таблица канала
static/js/composite.js       режимы наложения, композит в линейном свете
static/js/dither.js          дизеринг и вывод в canvas
static/js/doc.js             модель документа и строгая проверка
static/js/ui-kit.js          кирпичики интерфейса
static/js/panels.js          левая колонка: разделы и карточки каналов
static/js/engine.js          выбор движка: сервер или браузер
static/js/render.js          цикл рендера и сцена просмотра
static/js/library.js         библиотека пресетов
static/js/transfer.js        экспорт и импорт
static/js/boot.js            встроенный пресет и запуск
```

Границы файлов совпадают с прежними нумерованными секциями скрипта — код при
разделении не менялся ни на символ, только разъехался по файлам.

Два решения, которые легко нарушить по невнимательности:

* **Обычные `<script src>`, а не ES-модули.** Модули запрещены политикой
  источника при открытии страницы по `file://` — а этот путь обязан работать.
  Поэтому файлы делят одну глобальную область, а порядок подключения в
  `index.html` — снизу вверх по зависимостям. Каждый файл в шапке говорит,
  от чего зависит.
* **`tokens.css` — единственное место с константами оформления.** Ни один
  компонент не заводит своих цветов; исключения (тени, подсветки) видны в
  файле компонента и не притворяются токенами.

## 2. Главный инвариант: точная стыковка

Всё поле шума строится на решётке, у которой **число ячеек на плитку — целое**.
Координата выборки `x = X · cells / W`, поэтому при `X = W` она равна ровно
`cells`, то есть ровно периоду решётки. Левый край плитки тождественно равен
правому, верхний — нижнему. Никакой «склейки», зеркалирования или блендинга
краёв нет и не нужно.

Это выполняется для всех типов шума, любого числа октав, при искажении домена
и при любом размере плитки, включая нечётный. Обоснования для нетривиальных
случаев:

* **Октавы.** Частота октавы — `cells · lac^o`, лакунарность целая (2…4),
  значит число ячеек остаётся целым.
* **Искажение домена (warp).** Смещение берётся из такого же W/H-периодического
  поля. `base(x + P + w(x+P)) = base(x + P + w(x)) = base(x + w(x))`, потому что
  у `base` период ровно `P`. Композиция периодических функций остаётся
  периодической — стыковка не ломается.
* **Ворлей.** Индексы ячеек заворачиваются по модулю, а позиция точки берётся
  как `точка[завёрнутый] + (незавёрнутый − завёрнутый)` — это даёт корректное
  тороидальное расстояние.
* **Зерно + ВЧ-фильтр.** Размытие «коробкой» круговое (индексы заворачиваются),
  поэтому высокочастотная составляющая тоже периодична.

### Как это проверяется

Метрика: для каждой пары соседних столбцов (включая пару «последний ↔ первый»,
то есть сам стык) берётся средний модуль разности. Дальше разность на стыке
сравнивается с **распределением** внутренних разностей — с 95-м процентилем.

> **Ловушка, на которую я наступил.** Сначала я сравнивал со *средним* по
> внутренним парам. У блочного шума большинство внутренних пар нулевые (внутри
> блока), и стык давал отношение ×6 — ложная тревога. Сравнение с процентилем
> это лечит: стык блочного шума ничем не отличается от границы обычного блока.

Контрольный тест обязателен: поле строится шире плитки и обрезается не по
периоду. Такое поле обязано **провалить** проверку. Сейчас: у настоящих полей
стык ≈ 1× p95, у обрезанного — 7×. Без контроля метрика ничего не стоит.

## 3. Правило «никаких умолчаний»

Разбор JSON строгий в обе стороны: отсутствующее поле, лишнее поле, неверный тип
или значение вне диапазона — исключение с точным адресом:

```
документ.channels[0].noise.shape.gamma: поле отсутствует (обязательное) [файл: my.json]
```

Схема **union**: файл всегда несёт полный набор полей, включая те, что нужны
другим типам шума (`worleyMode` у зерна и т. п.). Это сделано намеренно —
иначе при переключении типа в интерфейсе пришлось бы откуда-то брать
недостающие значения, то есть подставлять умолчание. Файлы чуть длиннее,
зато пресет переносится без потерь и без догадок.

Заводские значения (`factoryNoise`) применяются **только** при явном создании
канала пользователем, никогда — для «починки» импортируемых данных.

Один и тот же валидатор написан дважды (JS и Zig) и выдаёт совпадающие тексты
ошибок — это проверяется тестом.

## 4. Цвет

OKHSL по Björn Ottosson. Выбран потому, что при любых `s` и `l` цвет остаётся
**внутри гамута sRGB по построению** — клиппинга не бывает вовсе (проверено на
4000 случайных точках, максимальный выход 0.0).

Конвейер цвета:

1. `okhsl → Oklab → линейный sRGB`;
2. интерполяция «низ → верх» в OKLab (перцептивно ровно) либо в линейном sRGB —
   переключается в разделе «Вывод»;
3. режимы наложения слоёв **всегда** в линейном свете по формуле композитинга
   W3C, непремультиплицированный аккумулятор;
4. линейный → sRGB через таблицу на 16385 точек с линейной интерполяцией
   (ошибка < 0.001 LSB, убирает `pow` из горячего цикла).

Цвет канала сворачивается в **таблицу на 2048 записей**, в которую уже заложена
«форма» (контраст, смещение, гамма, инверсия). Поэтому на пиксель приходится
одно обращение к таблице вместо десятка операций, и правка формы не требует
пересчёта шума.

## 5. Дизеринг

Убирает полосы (бэндинг) при переводе в 8 бит. Две вещи, до которых пришлось
дойти:

* **Позиционный, а не последовательный.** Изначально TPDF-шум брался из
  xorshift-состояния, идущего по пикселям подряд. Такой дизеринг зависит от
  порядка обхода — многопоточный расчёт по полосам дал бы другую картинку, чем
  однопоточный, и Zig никогда не совпал бы с JS. Сейчас значение считается
  из хэша координат: `hash2i(x, y, соль_компоненты)`, старшие и младшие 16 бит
  дают два равномерных числа для треугольного распределения.
* **Не трогать точные значения.** Шум добавляется только там, где квантование
  реально даёт ошибку: `if (|v − round(v)| > 1e-4)`. Иначе непрозрачная альфа
  255 половину времени превращалась в 254 (крап по всей плитке), а чистый чёрный
  0 — в 1. Дизерить нечего, когда ошибки квантования нет.

## 6. Два движка и дисциплина паритета

Движок на Zig — дословный порт браузерного. Держать их в согласии помогает
единственная вещь: **автоматическая попиксельная сверка**. `tests/test-parity.js`
считает все 10 пресетов обоими движками и сравнивает.

Текущее расхождение: **максимум 1 LSB**, при выключенном дизеринге чаще 0.
Источник — разный порядок округления `f32`/`f64` и последний бит `cos`/`sin`.
Порог теста — 2 LSB и меньше 0.5 % пикселей с расхождением больше 1.

Чтобы порт оставался дословным, соблюдаются мелочи:

* поля хранятся в `f32`, промежуточная арифметика в `f64` — как в JS, где
  `Float32Array` читается в число двойной точности;
* `hash2i` использует `*%` по `u32` — точный эквивалент `Math.imul` + `>>>`;
* таблица градиентов считается в `f64` и кладётся в `f32` — как в JS.

**Если правится алгоритм — правится в обоих файлах, и сверка перезапускается.**
Это единственная защита от расхождения.

## 7. Сервер

`POST /api/render` принимает **пачку** задач и возвращает сырой RGBA:

```
"ZRN1" | u32 количество | (u32 ширина, u32 высота) × N | пиксели подряд
```

Пачка — не украшение: за один запрос уходят главная плитка и миниатюры всех
каналов. Раньше клиент считал их по одной.

PNG сервер не кодирует: браузер делает это сам через `canvas.toBlob`, и это не
узкое место.

### Кэш шумовых полей

Ключ — хэш параметров шума **без «формы» и без цвета** плюс размер плитки.
Поэтому правка цвета, контраста, гаммы или режима наложения не пересчитывает
шум вовсе. Это самый частый случай при работе руками, и именно он даёт
основное ускорение (6.4 мс против 15.6 мс).

Кэш со счётчиком ссылок: `get` увеличивает счётчик, вытеснение трогает только
записи с нулём ссылок. Иначе параллельный запрос мог бы читать освобождённую
память. Кэш трогается **только из потока запроса**, не из рабочих потоков —
так не нужны блокировки внутри горячего кода.

### Параллелизм

Два этапа, оба без вложенности задач:

1. **Поля** — по одному, но каждое считается всеми ядрами по полосам строк.
   Так и одна большая плитка, и пачка мелких загружают процессор.
2. **Композит** — плоский список (задача × полоса строк). Композит независим
   по пикселям, поэтому полосы можно считать как угодно параллельно.

Вложенных `Io.Group` намеренно нет: если внешние задачи займут весь пул, а
внутренние не смогут запуститься, будет тупик. Плоские списки этого не допускают.

## 8. Производительность: что сделано и что осталось

Замеры на Ryzen 7 5800H (8 ядер / 16 потоков), пресет «тёмный холст», 3 канала.

| | JS | Zig |
|---|---|---|
| 512², правка цвета | 41 мс | 6.4 мс |
| 512², пересчёт шума | 41 мс | 15.6 мс |
| 1024², пересчёт шума | 266 мс | 52 мс |

Что дало эффект, по убыванию вклада:

1. **Кэш полей** — правка цвета вообще не считает шум.
2. **Пакетный запрос** — одна главная плитка + N миниатюр за один раз.
3. **Убран последовательный хвост.** `@memset` обнуления, нормировка и поиск
   min/max шли в один поток и по Амдалю душили масштабирование. Первая октава
   теперь *пишет* значение, а не накапливает (обнуление не нужно), нормировка
   и min/max слиты в один параллельный проход. Масштабирование 3.1× → 5.2×.
4. **Убрано целочисленное деление** из горячих циклов: в типичном случае
   координата уже внутри `[0, p)`, деление не нужно (`wrapI`).
5. **Предрасчёт по столбцам.** `@floor`, дробная часть и `fade` от `x` не
   зависят от строки. Перлин: 34 → 19.5 нс/px, value: 24.5 → 12.4 нс/px.

Что проверялось и **не** дало эффекта — чтобы не повторять:

* Уменьшение таблицы sRGB с 64 КБ до 16 КБ: разницы нет, откатил.
* Накладные расходы `Io.Group` — 0.4–5 мкс на задачу, это не узкое место.

Что осталось на столе:

* **Композит стоит ~52 нс/px** и масштабируется хуже построения шума. Внутри:
  3 обращения к цветовой таблице (32 КБ каждая), 3 к таблице sRGB (64 КБ),
  4 хэша дизеринга. Дизеринг — 21 % от этого времени. Напрашивается
  векторизация и обработка каналов внешним циклом с аккумулятором на полосу.
* **16 потоков медленнее 8** на работе, упирающейся в память (SMT). Возможно,
  стоит ограничивать число полос физическими ядрами, но определять их
  переносимо в 0.16 нечем.

## 9. Ловушки Zig 0.16

Версия свежая, API сильно переработан. Что пришлось выяснять по исходникам
стандартной библиотеки (`C:\Users\sibkit\.zvm\0.16.0\lib\std`), а не по памяти:

* **`zig build` собирал Debug.** `standardOptimizeOption(.{ .preferred_optimize_mode = ... })`
  не меняет умолчание, а лишь добавляет флаг `-Drelease`. Из-за этого первый
  замер показал Zig **в 5 раз медленнее** JS. Сейчас в `build.zig` стоит явное
  `b.option(...) orelse .ReleaseFast`. **Проверяйте размер бинарника:**
  Debug ≈ 2.5 МБ, ReleaseFast ≈ 1.1 МБ.
* `pub fn main(init: std.process.Init)` — из `init` берутся `io`, `gpa`, `arena`,
  аргументы.
* **`std.time.Timer` больше нет.** Время: `const CLK: std.Io.Clock = .awake;`
  затем `CLK.now(io)` и `t0.durationTo(...).toNanoseconds()`.
* **`std.Thread.Pool` больше нет.** Пул потоков живёт внутри `Io.Threaded`;
  доступ через `Io.Group.concurrent(io, fn, args)` и `group.@"await"(io)`.
  `await` до сих пор зарезервировано — нужен `@"await"`.
* Примитивы синхронизации переехали в `std.Io`: `Io.Mutex` (`lockUncancelable(io)` /
  `unlock(io)`), `Io.Condition`, `Io.Semaphore`.
* `std.ArrayList` безменеджерный: `.empty`, `append(gpa, x)`, `deinit(gpa)`.
  Метода `.writer()` у него нет — нужен `std.Io.Writer.Allocating` и `.written()`.
* Работа с файлами через `Io`: `Io.Dir.cwd()`, `openDir(io, path, .{})`,
  `readFileAlloc(io, path, gpa, .limited(N))`, `writeFile(io, .{...})`.
  Создание каталога — `createDirPath`, не `makeDir`. `selfExeDirPath` отсутствует.
* **Каталог нужно открывать с `.{ .iterate = true }`,** иначе обход падает.
  У меня из-за этого молча переписался пустой `noises/index.json` — ошибка
  глоталась через `catch null`. Теперь ошибка пробрасывается, и пустой список
  не записывается никогда.
* Имена `i0`, `i1` — примитивные типы, затеняние запрещено. Как и `h` рядом с
  параметром `h`.
* Рабочий образец HTTP-сервера в самой stdlib: `std/Build/WebServer.zig`.
  Лучший источник правды по `http.Server` + `Io.net`.

### Ловушки правки файлов (не Zig, но кусалось)

* Исходники были в **CRLF**, поэтому многострочные скриптовые замены молча не
  находили текст. Все `src/*.zig` переведены в LF — держите так.
* Скриптовая замена однажды записала в `index.html` **байты-управляющие символы**
  (включая NUL) внутрь регулярного выражения. Файл выглядел нормально, `grep`
  считал его бинарным, а функция работала неправильно. Если правите файл
  скриптом — потом сканируйте на символы < 0x20.

## 10. Проверки

```
zig build test              тесты движка Zig (бесшовность, крайние размеры, разбор)
zig build bench             замеры: нс/пиксель, масштабирование по потокам
cd tests && npm install     один раз, ставит jsdom
node tests/run-all.js       все наборы разом
```

Наборы:

| файл | что проверяет | нужен сервер |
|---|---|---|
| `src/test.zig` | ядро Zig: стыковка, вырожденные решётки, октавы, разбор | — |
| `tests/test-engine.js` | ядро JS: цвет, периодичность, композит, валидация | — |
| `tests/make-presets.js` | генерирует `noises/*.json` и проверяет каждый | — |
| `tests/test-ui.js` | интерфейс в jsdom, **запасной путь на JS** | нет |
| `tests/test-parity.js` | попиксельная сверка Zig и JS + замеры | да |
| `tests/test-ui-zig.js` | тот же интерфейс против живого сервера | да |

Тесты интерфейса ждут **готовности** (`stState === 'готов'`), а не фиксированной
паузы. Под нагрузкой фиксированные паузы давали ложные провалы.

Код страницы наборы берут через `tests/load-app.js`: он читает список
`<script src>` из `index.html` и склеивает файлы **в том же порядке**, в каком
их грузит браузер. Забытое подключение или пропавший файл — исключение, а не
тихо урезанный набор проверок. Границу «движок без DOM» модуль проводит по
`doc.js`: наборы ядра берут всё до него включительно.

## 11. Если продолжать

По убыванию пользы:

1. **Векторизовать композит** — сейчас это самая дорогая часть на пиксель и
   хуже всех масштабируется.
2. **Кодировать PNG на сервере** (`std.compress.flate.Compress` есть в 0.16) —
   пригодится для плиток 2048² и выше.
3. Отдавать превью **прогрессивно**: сначала уменьшенную плитку, потом полную.
   Ощущается сильнее, чем ещё 30 % чистой скорости.
4. Сжимать ответ рендера — сейчас 1024² это 4 МБ сырых байт по петле;
   на localhost терпимо, но это самый большой кусок трафика.
