# Как это устроено

Записка для того, кто вернётся к проекту без памяти о том, как он делался.
Здесь только неочевидное: решения и их причины, найденные ловушки, замеры.
Что умеет программа и как ей пользоваться — в `README.md`.

## 1. Карта кода

```
Cargo.toml            workspace: engine + app; release — thin LTO
rust-toolchain.toml   Rust 1.99 (edition 2024); системный 1.80 слишком стар
.cargo/config.toml    target-cpu=x86-64-v2 для Windows
engine/               крейт zerno-engine: чистый движок, без Tauri
  src/color.rs          Oklab / OKHSL, таблица линейный → sRGB
  src/doc.rs            модель документа, строгий разбор JSON
  src/noise.rs          решётки, шумы, искажение домена, размытие зерна
  src/composite.rs      форма, цветовые таблицы, наложение, дизеринг
  src/render.rs         Engine: пакет задач → ZRN1, кэш полей
  src/bin/zerno-render.rs  stdin JSON → stdout ZRN1 (для сверки с эталоном)
  tests/fields.rs       стыковка, вырожденные решётки, кэш, ошибки запроса
  examples/             bench (пресеты), fields (поля по потокам)
app/                  крейт zerno: оболочка Tauri 2
  src/main.rs           команды render, engine_info; запуск
  src/files.rs          настройки, библиотека, открыть/сохранить, экспорт
  tauri.conf.json       окно, CSP, frontendDist = ui
  capabilities/         разрешения: core, dialog (ask/message)
  ui/                   интерфейс (вшивается в exe)
    index.html            разметка и список подключений
    css/                  tokens → base → layout → components/*
    fonts/                IBM Plex Sans/Mono, Unbounded (латиница + кириллица)
    js/                   color, model, doc, ui-kit, history, panels, engine,
                          render, library, transfer, keys, help, boot
presets/              пресеты из комплекта (генерирует tools/make-presets.js)
docs/                 эта записка
package.json          jsdom для проверок интерфейса (npm install)
tests/                проверки на Node; tests/reference — эталон на JS
tools/                make-presets.js — пресеты, make-icon.js — иконка
```

Правило раскладки: у каждой папки одно назначение. Rust — `engine/` и `app/`,
всё, что попадает в exe, — внутри `app/`; всё на Node вне приложения — `tests/`
(проверки) и `tools/` (генераторы), зависимости Node — в корне.

История: сначала всё считалось в браузере на JS, потом появился сервер на
Zig (браузер — запасной путь), теперь — приложение на Rust + Tauri. Состояние
до перехода сохранено в первом коммите репозитория (`6953c6e`).

Движок на JS из приложения **убран**: два пути расчёта в интерфейсе означали,
что где-то тихо считает не тот. Он оставлен в `tests/reference` как эталон для
сверки и как подмена движка в проверках интерфейса.

### Решения, которые легко нарушить

* **Без сборщика и без tauri-cli.** Интерфейс — обычные `<script src>`,
  общая глобальная область, порядок подключения — снизу вверх по
  зависимостям, каждый файл в шапке говорит, от чего зависит. Tauri
  собирается обычным `cargo build`: в `app/Cargo.toml` фича
  `custom-protocol` включена по умолчанию (без неё exe ищет dev-сервер),
  `withGlobalTauri: true` даёт `window.__TAURI__` без npm-пакетов.
* **Нет `window.__TAURI__` — нет интерфейса.** `boot.js` показывает ошибку,
  а не считает чем-то другим.
* **`tokens.css` — единственное место с константами оформления.** Ни в
  других CSS, ни в JS цветов нет: JS берёт их через `cssToken()` (ui-kit.js),
  который читает переменную один раз и кэширует — сцена спрашивает `--acc` на
  каждом кадре, а `getComputedStyle` пересчитывает стили. Нет переменной —
  исключение. Проверка интерфейса загружает токены прямо из `tokens.css`
  (jsdom CSS не грузит). Исключение — цвета обрамления сцены `SURROUND`: это
  нейтральные образцы для оценки плитки, а не оформление.
* **Оформление — «эспрессо» в раскладке бенто.** Шапка, сцена, библиотека,
  строка состояния и каждый раздел левой колонки — отдельные скруглённые
  плитки (`--r-lg`) на подложке `--bg` с зазором `--gap`; общий вид плитки —
  одно правило в `layout.css`. У левой колонки `scrollbar-gutter: stable`:
  раскрытие раздела не сдвигает плитки на ширину полосы прокрутки.
* **Заливка окна = `--bg`.** Окно показывается сразу, а WebView2 поднимает
  свой браузерный процесс 0.5–2 с (холодный старт); всё это время видна
  `backgroundColor` из `tauri.conf.json`. Она должна совпадать с `--bg`,
  иначе запуск начинается с чужого (раньше — почти чёрного) прямоугольника.
  Совпадение проверяет тест интерфейса.
* **Пределы и перечисления — в одном месте на сторону.** В интерфейсе это
  `app/ui/js/model.js` (типы шума, режимы, `TILE_MIN/TILE_MAX`, `MIN_CELL_PX`),
  в движке — `engine/src/doc.rs`. Тексты ошибок одинаковые.

## 2. Главный инвариант: точная стыковка

Всё поле шума строится на решётке, у которой **число ячеек на плитку — целое**.
Координата выборки `x = X · cells / W`, поэтому при `X = W` она равна ровно
`cells`, то есть ровно периоду решётки. Левый край плитки тождественно равен
правому, верхний — нижнему. Никакой «склейки», зеркалирования или блендинга
краёв нет и не нужно.

Это выполняется для всех типов шума, любого числа октав, при искажении домена
и при любом размере плитки, включая нечётный. Обоснования для нетривиальных
случаев:

* **Октавы.** Частота октавы — `cells · lac^o`, лакунарность целая (2…4),
  значит число ячеек остаётся целым.
* **Искажение домена (warp).** Смещение берётся из такого же W/H-периодического
  поля. `base(x + P + w(x+P)) = base(x + P + w(x)) = base(x + w(x))`, потому что
  у `base` период ровно `P`. Композиция периодических функций остаётся
  периодической — стыковка не ломается.
* **Ворлей.** Индексы ячеек заворачиваются по модулю, а позиция точки берётся
  как `точка[завёрнутый] + (незавёрнутый − завёрнутый)` — это даёт корректное
  тороидальное расстояние.
* **Зерно + ВЧ-фильтр.** Размытие «коробкой» круговое (индексы заворачиваются),
  поэтому высокочастотная составляющая тоже периодична.

### Как это проверяется

Метрика: для каждой пары соседних столбцов (включая пару «последний ↔ первый»,
то есть сам стык) берётся средний модуль разности. Дальше разность на стыке
сравнивается с **распределением** внутренних разностей — с 95-м процентилем.

> **Ловушка, на которую я наступил.** Сначала я сравнивал со *средним* по
> внутренним парам. У блочного шума большинство внутренних пар нулевые (внутри
> блока), и стык давал отношение ×6 — ложная тревога. Сравнение с процентилем
> это лечит: стык блочного шума ничем не отличается от границы обычного блока.

Контрольный тест обязателен: поле строится шире плитки и обрезается не по
периоду. Такое поле обязано **провалить** проверку. Сейчас: у настоящих полей
стык ≈ 1× p95, у обрезанного — 7×. Без контроля метрика ничего не стоит.

## 3. Правило «никаких умолчаний»

Разбор JSON строгий в обе стороны: отсутствующее поле, лишнее поле, неверный тип
или значение вне диапазона — исключение с точным адресом:

```
документ.channels[0].noise.shape.gamma: поле отсутствует (обязательное) [файл: my.json]
```

Схема **union**: файл всегда несёт полный набор полей, включая те, что нужны
другим типам шума (`worleyMode` у зерна и т. п.). Это сделано намеренно —
иначе при переключении типа в интерфейсе пришлось бы откуда-то брать
недостающие значения, то есть подставлять умолчание. Файлы чуть длиннее,
зато пресет переносится без потерь и без догадок.

Заводские значения (`factoryNoise`) применяются **только** при явном создании
канала пользователем, никогда — для «починки» импортируемых данных.

Один и тот же валидатор написан дважды (JS в `app/ui/js/doc.js` и Rust в `engine/src/doc.rs`)
и выдаёт совпадающие тексты ошибок — это проверяется тестом.

## 4. Цвет

OKHSL по Björn Ottosson. Выбран потому, что при любых `s` и `l` цвет остаётся
**внутри гамута sRGB по построению** — клиппинга не бывает вовсе (проверено на
4000 случайных точках, максимальный выход 0.0).

Конвейер цвета:

1. `okhsl → Oklab → линейный sRGB`;
2. интерполяция «низ → верх» в OKLab (перцептивно ровно) либо в линейном sRGB —
   переключается в разделе «Вывод»;
3. режимы наложения слоёв **всегда** в линейном свете по формуле композитинга
   W3C, непремультиплицированный аккумулятор;
4. линейный → sRGB через таблицу на 16385 точек с линейной интерполяцией
   (ошибка < 0.001 LSB, убирает `pow` из горячего цикла).

Цвет канала сворачивается в **таблицу на 2048 записей**, в которую уже заложена
«форма» (контраст, смещение, гамма, инверсия). Поэтому на пиксель приходится
одно обращение к таблице вместо десятка операций, и правка формы не требует
пересчёта шума.

## 5. Дизеринг

Убирает полосы (бэндинг) при переводе в 8 бит. Две вещи, до которых пришлось
дойти:

* **Позиционный, а не последовательный.** Изначально TPDF-шум брался из
  xorshift-состояния, идущего по пикселям подряд. Такой дизеринг зависит от
  порядка обхода — многопоточный расчёт по полосам дал бы другую картинку, чем
  однопоточный, и движок никогда не совпал бы с эталоном. Сейчас значение считается
  из хэша координат: `hash2i(x, y, соль_компоненты)`, старшие и младшие 16 бит
  дают два равномерных числа для треугольного распределения.
* **Не трогать точные значения.** Шум добавляется только там, где квантование
  реально даёт ошибку: `if (|v − round(v)| > 1e-4)`. Иначе непрозрачная альфа
  255 половину времени превращалась в 254 (крап по всей плитке), а чистый чёрный
  0 — в 1. Дизерить нечего, когда ошибки квантования нет.

## 6. Эталон и движок: дисциплина паритета

Движок на Rust — порт эталона на JS (`tests/reference`), а тот, в свою
очередь, совпадал с прежним движком на Zig. Держать их в согласии помогает
единственная вещь: **автоматическая попиксельная сверка**. `tests/test-parity.js`
считает все пресеты эталоном и `zerno-render.exe` и сравнивает.

Текущее расхождение: **максимум 1 LSB**, при выключенном дизеринге чаще 0.
С прежним Zig Rust совпадал **бит в бит** на всех пресетах (с дизерингом и
без) — это проверялось при переносе, пока Zig был жив.

Чтобы порт оставался дословным, соблюдаются мелочи:

* поля хранятся в `f32`, промежуточная арифметика в `f64` — как в JS, где
  `Float32Array` читается в число двойной точности;
* `hash2i` — `wrapping_mul` по `u32`, точный эквивалент `Math.imul` + `>>>`;
* таблица градиентов считается в `f64` и кладётся в `f32`;
* порядок операций в формулах не «упрощается»: `a*b+c` и `c+a*b` в `f32`
  дают разные младшие биты.

**Если правится алгоритм — правится и эталон, и сверка перезапускается.**

## 7. Приложение

### Рендер

Команда `render` принимает `{"jobs":[{"width","height","doc"}]}` и возвращает
**двоичный** ответ (`tauri::ipc::Response` → `ArrayBuffer` в JS):

```
"ZRN1" | u32 количество | (u32 ширина, u32 высота) × N | RGBA подряд
```

За один вызов уходят главная плитка и миниатюры всех каналов. JSON с
массивом чисел или base64 для 1024² — это мегабайты текста и десятки мс на
разбор; двоичный ответ эти расходы убирает.

Тяжёлые команды идут через `spawn_blocking`: окно не замирает, пока считается.

### Живой рендер вместо задержки

Раньше перерисовка ждала паузы в правках (debounce) — при перетаскивании
ползунка картинка стояла. Теперь `render.js` держит насос `{busy, dirty}`:
правка ставит `dirty`; если кадр не считается — считается сразу; если
считается — по окончании сразу считается следующий с последним состоянием.
Кадров «впрок» не бывает, устаревших — тоже, статус «готов» ставится только
когда `dirty` снят.

### Сцена без дёрганья

Раньше готовая плитка становилась PNG-blob и фоном (`background-image`) сцены,
а прежний URL сразу отзывался. Картинка декодируется асинхронно, и на время
декодирования фон пропадал — при перетаскивании ползунка сцена мигала. Вторая
причина — строка состояния: ширина «рендер»/«готов» и числа мс менялась, и
соседние поля прыгали.

Теперь плитка кладётся `putImageData` в постоянный canvas (`preview.tile`), а
`drawStage()` **синхронно** заливает сцену узором из него: масштаб и сдвиг —
`DOMMatrix` узора, сетка и уголки центральной плитки — линиями на том же
canvas. Перерисовка — по готовности кадра, по масштабу и по `ResizeObserver`.
У полей состояния и времени фиксированная ширина. Цвет акцента берётся из
`--acc` (`cssToken` бросает исключение, если переменной нет).

### Понятность интерфейса

* **Справка вместо подсказок.** Всплывающих подсказок нет совсем (ни `title`,
  ни строки подсказок — проверяется тестом). Тексты — разделы
  `<article data-topic data-title>` в `index.html`, оглавление строит
  `help.js`. Значок «?» — `helpBtn(topic)`: у `makeSection(…, topic)` он
  обязателен, у `subHead(…, topic)` — строка или явный `null`. Несуществующий
  раздел — исключение уже при сборке значка, ссылки `data-go` между разделами
  проверяются при запуске.
* **Размер пятна по ступеням.** Ячеек на плитку всегда целое число
  (`cellsFor` = `round(D/s)` в пределах `[1; maxCellsFor]`, для решёточных
  типов — не больше `D/2`), поэтому между соседними допустимыми размерами
  ничего нет. Ползунок логарифмический (`makeRow({log})`), встаёт на `D/cells`,
  под подписью — «N ячеек». Раньше ползунок двигался плавно, а картинка
  менялась скачками — казалось, что он «дёргает».
* **Цвет — градиент с ручками** (`buildStops`): одна полоса «слабый → сильный»
  вместо двух редакторов подряд, редактор — у выбранной ручки.
* **Колесо над сценой** — масштаб без `Ctrl` (прокручивать сцене нечего),
  двойной клик — 1:1.
* **Справка** — `F1`/«?» открывают «Начало»; `Esc`, ✕ и клик мимо закрывают.
* **Миниатюры типов** на кнопках «+ канал» — `makeTypeThumbs()` при запуске
  рендерит каждый тип движком (постоянный сид, серые цвета).
* **Стрелка на карточке канала**: заголовок занят полем имени, без стрелки
  было неочевидно, что карточка раскрывается.

### Кэш шумовых полей

Ключ (`FieldKey`) — **все** параметры шума без «формы» и цвета, плюс размер
плитки; `f64` сравниваются побитно. Не хэш: у хэша бывают коллизии, а
коллизия здесь — молча чужая картинка. Правка цвета, контраста, гаммы или
режима наложения не пересчитывает шум вовсе — 2 мс против 11 на 512².

Поля лежат в `Arc<Field>`; вытеснение (LRU по метке времени, лимит 256 МБ)
трогает только записи, которыми сейчас никто не пользуется
(`Arc::strong_count == 1`). Нехватка памяти на поле — `FieldError::OutOfMemory`
(`try_reserve_exact`), а не падение процесса.

### Параллелизм (rayon)

1. **Поля** — по одному, каждое всеми ядрами полосами строк (не меньше 24
   строк в полосе). Вертикальное размытие зерна тоже идёт полосами со своими
   скользящими суммами.
2. **Композит** — плоский список (задача × полоса строк) через
   `into_par_iter`, полос примерно вдвое больше потоков. Вложенного
   параллелизма нет.

### Файлы

* **Настройки** — `app_config_dir/settings.json`, ровно `{"libraryDir": …}`.
  Нет файла — папка не выбрана; файл испорчен — ошибка, а не тихий сброс.
* **Запись** — во временный файл и `rename`: оборванная запись не оставит
  полупустой пресет. Перед записью документ разбирается тем же строгим
  разбором, что и при чтении.
* **Обход папки** собирает ошибки по файлам и показывает их списком: раньше
  ошибка обхода проглатывалась, и библиотека молча становилась пустой.
* **PNG** кодирует Rust (`png`, без потерь); сначала диалог, потом рендер —
  отмена ничего не считает. **WebP** кодирует WebView2 (`canvas.toBlob`), а
  байты уходят в Rust сырым телом запроса (`tauri::ipc::Request`, имя файла —
  в заголовке, в %-кодировке).
* Имя файла из имени пресета — только запрещённые Windows символы → `_`.
  Раньше транслитерация превращала любое кириллическое имя в `_____`, и
  разные пресеты молча перезаписывали один файл.

### История правок

Шаг истории — `{s, file}`: снимок документа в JSON (ровно то, что пишется в
файл) **и путь связанного файла**. Путь в каждом шаге — иначе после отмены
старое содержимое ушло бы по `Ctrl+S` в файл, открытый позже. Правки чаще
350 мс сливаются в один шаг. Признак «изменено» — сравнение текущего снимка со
снимком, совпадающим с диском (`savedSnap[path]`). Сессия пишется в
`localStorage` через 600 мс после правки и при закрытии окна.

### OKLCH в редакторе цвета

Хранение не меняется — OKHSL. OKLCH — только способ правки: `L` и `C` из
Oklab, тон `H` — тот же угол, что у OKHSL. Граница гамута при данных `L, H`
— `getCs(L, a, b)[2]` из того же порта Ottosson (`maxChroma`).
`oklchToOkhsl` бросает исключение, если `C` за границей: молча обрезать — значит
сохранить не тот цвет. Редактор помнит «желаемую» хрому: если при новых `L`
или `H` она не помещается, `C` снижается до границы с видимой подписью, а при
возврате `L/H` хрома возвращается к заказанной.

## 8. Производительность

Ryzen 7 5800H (8 ядер / 16 потоков), пресет «тёмный холст», 3 канала,
`cargo run --release -p zerno-engine --example bench`:

| | правка цвета | пересчёт шума | Zig, пересчёт |
|---|---|---|---|
| 512² | 2.0 мс | 10.8 мс | 15.6 мс |
| 1024² | 7.7 мс | 40 мс | 52 мс |
| 2048² | 33 мс | 154 мс | 188 мс |

В несколько потоков Rust быстрее Zig. В один поток путь с искажением
домена был медленнее Zig примерно на 15 % — из-за проверок границ срезов.

**Чтение без проверки границ** (`crate::at`, `get_unchecked`) — только в
горячих циклах шума: выборки решёток, строки с искажением, Ворлей. Правила:

* одна функция `at` на весь крейт, у каждого вызова — комментарий `SAFETY`
  с доказательством, что индекс в границах;
* инварианты, на которых держатся доказательства (решётка не пустая, строка
  искажения той же длины, таблица столбцов построена для этой решётки),
  проверяются обычным `assert!` один раз на строку, а не на пиксель;
* в отладочной сборке и в `cargo test` `at` сверяет каждый индекс
  (`debug_assert!`), так что тесты ловят ошибку как обычную панику.

Эффект в один поток: искажение 65.7 → 60.1 нс/px, Ворлей 51.2 → 47.6,
Value 11.4 → 10.1, Перлин 19.7 → 19.1. В композите то же самое замерено и
**не** дало ничего (14.9 против 14.8–15.2 мс на 512²) — там проверки
оставлены: `unsafe` без измеримого выигрыша не нужен.

Что дало эффект:

1. **Кэш полей** и **пакетный рендер** — см. раздел 7.
2. **Const generics** `<FIRST, RIDGED>` для строк Перлина/Value (макрос
   `rows_dispatch!`): ветки «первая октава пишет, а не копит» и «гребни»
   выносятся из пиксельного цикла на этапе компиляции.
   Перлин 22.6 → 19.5 нс/px, Value 15.2 → 11.0, с искажением 69 → 63.
3. **Нормировка и min/max** в один параллельный проход; первая октава пишет
   значение, обнуление не нужно.
4. **Без целочисленного деления** в горячем цикле (`wrap_i`): координата
   почти всегда уже в `[0, p)`.
5. **Предрасчёт по столбцам**: `floor`, дробная часть и `fade` от `x` не
   зависят от строки.

Что проверялось и **не** дало эффекта — чтобы не повторять:

* `target-cpu=native` и `x86-64-v2` — в пределах шума (v2 оставлен: не хуже
  и работает на любом x86-64 последних 15 лет);
* `zip`-итераторы вместо индексов — медленнее, откатил;
* уменьшение таблицы sRGB с 64 КБ до 16 КБ (ещё на Zig) — разницы нет.

## 9. Ловушки

### Rust и Tauri

* **Системный Rust 1.80 не собирает Tauri 2.12** (edition 2024, свежие
  зависимости). Версия закреплена в `rust-toolchain.toml`, rustup ставит её сам.
* **Без фичи `custom-protocol`** exe ищет dev-сервер и показывает пустое
  окно. В `app/Cargo.toml` она в `default`.
* **`opt-level = 3` для движка в dev-профиле** (`[profile.dev.package.zerno-engine]`):
  иначе отладочная сборка приложения рисует 512² секундами и кажется сломанной.
* **CSP**: `connect-src ipc: http://ipc.localhost` — без этого `invoke` не
  ходит; `img-src data:` — для зерна оформления и миниатюр типов шума.
  `blob:` не нужен: превью — canvas, а не картинка.
* Ошибка команды приходит в JS **строкой**, а не `Error` — `engine.js`
  оборачивает её, чтобы у `toast(e.message)` было что показать.
* `onDragDropEvent` даёт пути файлов, а не содержимое: брошенный файл читает
  Rust (`doc_read`).

### Правка файлов (кусалось не раз)

* Многострочные `heredoc` и `python -c` в Git Bash портили `\n` в строках
  JS — в `boot.js` однажды оказались переводы строки внутри литералов.
  После скриптовой правки: `node --check app/ui/js/*.js`.
* Файлы держатся в LF (`.gitattributes`); скриптовые замены по CRLF молча
  ничего не находят.

### Ловушки Zig 0.16 (для истории)

Сервер на Zig удалён; записка о его ловушках — в `how_it_made.md` коммита
`6953c6e`. Главная из них стоит повторения в любом языке: **ошибка обхода
каталога, проглоченная через `catch null`, однажды молча переписала список
библиотеки пустым.**

## 10. Проверки

```
cargo test -p zerno-engine                 тесты движка
cargo build --release -p zerno-engine      нужен zerno-render.exe для сверки
npm install                                один раз, ставит jsdom
node tests/run-all.js                      все наборы на Node
```

| файл | что проверяет |
|---|---|
| `engine/tests/fields.rs` | стыковка, контрольная обрезка, вырожденная ячейка, нечётные размеры, лимит октав, каналы после 64-го, кэш, ошибки запроса |
| `engine/src/*.rs` (`#[cfg(test)]`) | гамут OKHSL, обратимость, разбор документа |
| `tests/test-engine.js` | эталон: цвет, периодичность, композит, валидация |
| `tools/make-presets.js` | генерирует `presets/*.json` и проверяет каждый |
| `tests/test-parity.js` | попиксельная сверка Rust и эталона, ошибки, пакет, скорость |
| `tests/test-ui.js` | интерфейс в jsdom с заглушкой `__TAURI__` |

`run-all.js` без jsdom или без `zerno-render.exe` **падает с объяснением**, а не
пропускает наборы.

Проверка интерфейса подменяет `window.__TAURI__`: `render` считает эталон,
файловые команды пишут в журнал и отвечают заданным. Так проверяются клавиши,
история, привязка к файлу, библиотека с ошибками, экспорт, перетаскивание
файла и то, что ошибка движка видна, а следующая правка снова рисует.
Тесты ждут **готовности** (`stState === 'готов'`), а не фиксированной паузы.

`tests/load-app.js` читает список `<script src>` из `app/ui/index.html` и склеивает
файлы в том же порядке, что WebView. Эталон вставляется перед `doc.js`.

Что тесты уже поймали (не гипотетически):

* миниатюру 6 px у плитки 8×N — движок принимает сторону от 8 (раньше JS-путь
  это не проверял);
* обрыв перетаскивания ползунка ширины (пересборка колонки уничтожала ползунок);
* утечку памяти при отказе построения поля (ещё на Zig);
* порчу списка библиотеки из-за проглоченной ошибки обхода каталога;
* крап дизеринга по непрозрачной альфе.

## 11. Если продолжать

По убыванию пользы:

1. **Векторизовать композит** — самая дорогая часть на пиксель
   (3 таблицы цвета, таблица sRGB и хэши дизеринга на пиксель).
2. **Прогрессивное превью** для больших плиток: сначала уменьшенная, потом
   полная — ощущается сильнее, чем ещё 30 % чистой скорости.
3. Отмена устаревшего кадра внутри движка (флаг, проверяемый между полосами):
   сейчас насос не запускает лишних кадров, но начатый досчитывается.
4. Сборка установщика (`bundle.active`) — сейчас приложение один exe.
